### Class Structure Template for Mediator Pattern
[Source: architecture/coding-standards.md]
```objectscript
/// Gang of Four Mediator Pattern - Object Interaction Management
Class Patterns.GoF.Behavioral.Mediator Extends %RegisteredObject
{
    /// Notify mediator of an event from a colleague
    Method Notify(pSender As Colleague, pEvent As %String) As %Status [ Abstract ]
    {
        Quit $$$OK
    }
    
    /// Register a colleague with the mediator
    Method RegisterColleague(pColleague As Colleague) As %Status [ Abstract ]
    {
        Quit $$$OK
    }
    
    /// Deregister a colleague from the mediator
    Method DeregisterColleague(pColleague As Colleague) As %Status [ Abstract ]
    {
        Quit $$$OK
    }
}

/// Abstract colleague that communicates through mediator
Class Patterns.GoF.Behavioral.Colleague Extends %RegisteredObject
{
    /// Reference to the mediator
    Property Mediator As Mediator;
    
    /// Send message through mediator
    Method Send(pMessage As %String) As %Status
    {
        If $IsObject(..Mediator) {
            Quit ..Mediator.Notify($THIS, pMessage)
        }
        Quit $$$ERROR($$$GeneralError, "No mediator set")
    }
    
    /// Receive message from mediator
    Method Receive(pMessage As %String) As %Status [ Abstract ]
    {
        Quit $$$OK
    }
}
```

### Mediator Pattern Specific Considerations
- **Communication Types**: Synchronous, asynchronous, broadcast, targeted
- **Message Format**: Define clear message structure and protocols
- **Colleague Identity**: Unique identification for message routing
- **Event Ordering**: Maintain message order when required
- **Error Propagation**: Handle communication failures gracefully
- **Performance**: Avoid mediator becoming a bottleneck
- **Scalability**: Support dynamic colleague addition/removal
- **Memory Management**: Clean up references to prevent leaks

### ObjectScript-Specific Communication Features
[Source: architecture/coding-standards.md]
- **$CLASSMETHOD**: Dynamic method invocation for callbacks
- **%DynamicObject**: Flexible message payload structure
- **Jobs**: Background processing for async communication
- **Globals**: Persistent message queue if needed
- **$SYSTEM.Event**: Native event signaling (if available)
- **Lock Commands**: Synchronization for shared resources

### Event-Based Communication Design
- Event types: Request, Response, Notification, Alert
- Event payload: Sender, Receiver, Type, Priority, Data, Timestamp
- Subscription model: Topic-based or content-based filtering
- Event persistence: Optional storage for audit/replay
- Event correlation: Link related events (request/response pairs)
- Error events: Special handling for system errors
- Event metrics: Track throughput, latency, failures

### Key Implementation Notes for Mediator Pattern
- Primary focus: Centralizing complex object interactions
- Prevent n-to-n colleague relationships becoming unmaintainable
- Healthcare context: Critical for department coordination and patient flow
- Event-based approach provides flexibility and audit capability
- Performance critical when mediating many colleagues
- Memory management important to prevent reference cycles
- Consider implementing observer pattern for event distribution
- Document trade-offs between centralization and potential bottleneck

### Service Layer Pattern Specific Considerations

- **Application Boundary**: Service Layer defines what operations the application can perform
- **Coarse-Grained Operations**: Service methods represent complete business operations, not fine-grained data access
- **Transaction Boundaries**: Each service operation defines a transaction scope (TSTART/TCOMMIT)
- **Domain Coordination**: Services coordinate multiple domain objects (Domain Model + Table Module)
- **Remote Facade**: Service Layer can serve as entry point for remote clients
- **Business Logic Location**: Services contain workflow/orchestration logic, not core business rules (those stay in domain objects)
- **Error Handling**: Services translate domain exceptions into service-level errors
- **Stateless**: Service Layer should be stateless; state lives in domain objects or database
- **API Design**: Service methods should be use-case oriented, reflecting business operations

### IRIS Transaction Management

[Source: architecture/tech-stack.md, coding-standards.md]
- **TSTART**: Begin transaction (supports nested transactions with transaction levels)
- **TCOMMIT**: Commit transaction (only commits when transaction level reaches 0)
- **TROLLBACK**: Rollback transaction (reverses all changes since TSTART)
- **$TLEVEL**: Special variable indicating current transaction nesting level
- **TSTART n**: Start transaction at specific nesting level
- **Lock Management**: Locks are automatically released on TROLLBACK
- **Isolation Levels**: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE
- **Savepoints**: Named transaction savepoints for partial rollbacks
- **Deadlock Detection**: Automatic deadlock detection and resolution

### Service Layer Architecture Pattern

Service Layer sits between presentation layer and domain/data access layers:
```
Presentation Layer (UI/API)
         ↓
   Service Layer ← Defines application boundary & transaction scope
         ↓
Domain Model + Table Module ← Business logic & data access
         ↓
   Database (IRIS)
```

### Healthcare Clinical Services Requirements

- **Patient Admission Service**: Coordinate admission workflow (create/update patient, assign bed, create admission record)
- **Patient Discharge Service**: Coordinate discharge workflow (update records, release bed, finalize billing)
- **Patient Transfer Service**: Transfer patient between departments/facilities
- **Transaction Scope**: Each service operation is a complete transaction
- **Domain Coordination**: Services orchestrate Patient (Domain Model) + PatientTableModule (Table Module) + other domain objects
- **Validation**: Service-level validation before domain operations
- **Error Handling**: Meaningful service exceptions (AdmissionFailed, DischargeFailed, etc.)
- **Audit Trail**: Log all clinical service operations for compliance

### Service Layer vs Other Patterns

- **Service Layer vs Transaction Script**: Service Layer coordinates domain objects; Transaction Script contains all logic procedurally
- **Service Layer vs Domain Model**: Service Layer orchestrates; Domain Model contains business rules
- **Service Layer vs Table Module**: Service Layer coordinates; Table Module handles table-specific operations
- **Service Layer vs Facade**: Service Layer defines application operations; Facade simplifies existing subsystem
- **When to use Service Layer**: Multi-layered architecture, remote access, transaction boundaries, complex workflows
- **When NOT to use**: Simple CRUD apps, single-layer systems, no transaction complexity

### Class Structure Template for Service Layer Pattern

[Source: architecture/coding-standards.md]
```objectscript
/// PoEAA Service Layer Pattern - Application Boundary Definition
Class Patterns.PoEAA.DomainLogic.ServiceLayer Extends %RegisteredObject
{
    /// Service name for logging and identification
    Parameter SERVICENAME;
    
    /// Execute operation within transaction boundary
    ClassMethod ExecuteInTransaction(pOperation As %String, pArgs... As %String) As %Status
    {
        Set tSC = $$$OK
        Set tResult = ""
        
        Try {
            // Begin transaction
            TSTART
            
            // Execute operation
            Set tSC = $METHOD($THIS, pOperation, pArgs...)
            
            // Commit if successful
            If $$$ISOK(tSC) {
                TCOMMIT
            } Else {
                TROLLBACK
            }
            
        } Catch ex {
            // Rollback on exception
            If $TLEVEL > 0 TROLLBACK
            Set tSC = ex.AsStatus()
        }
        
        Quit tSC
    }
    
    /// Validate service request
    ClassMethod ValidateRequest(pRequest As %DynamicObject) As %Status
    {
        Set tSC = $$$OK
        // Validation logic
        Quit tSC
    }
}
```

### Healthcare Patient Admission Service Example

```objectscript
Class Patterns.Examples.Clinical.PatientAdmissionService Extends Patterns.PoEAA.DomainLogic.ServiceLayer
{
    /// Admit patient with full transaction management
    ClassMethod AdmitPatient(pPatientData As %DynamicObject) As %Status
    {
        Set tSC = $$$OK
        
        Try {
            TSTART
            
            // 1. Validate admission request
            Set tSC = ..ValidateAdmissionRequest(pPatientData)
            If $$$ISERR(tSC) Quit
            
            // 2. Create or update patient (Domain Model)
            Set tPatient = ##class(Patient).CreateOrUpdate(pPatientData)
            Set tSC = tPatient.%Save()
            If $$$ISERR(tSC) Quit
            
            // 3. Assign bed via Table Module
            Set tSC = ##class(BedManagementTableModule).AssignBed(tPatient.%Id())
            If $$$ISERR(tSC) Quit
            
            // 4. Create admission record
            Set tSC = ..CreateAdmissionRecord(tPatient.%Id(), pPatientData)
            If $$$ISERR(tSC) Quit
            
            TCOMMIT
            
        } Catch ex {
            If $TLEVEL > 0 TROLLBACK
            Set tSC = ex.AsStatus()
        }
        
        Quit tSC
    }
}
```

### Transaction Management Best Practices

[Source: architecture/coding-standards.md]
- Keep transactions as short as possible
- Never include user interaction within transaction boundaries
- Use appropriate isolation levels for operation requirements
- Handle deadlocks gracefully with retry logic
- Log all transaction failures for debugging
- Use TROLLBACK liberally on any error condition
- Check $TLEVEL before TCOMMIT/TROLLBACK to prevent errors
- Document transaction boundaries in service method documentation
- Consider using savepoints for complex multi-step operations
- Monitor transaction lock timeouts

### Error Handling Requirements

[Source: architecture/coding-standards.md]
- Return %Status from all service methods
- Use $$$OK and $$$ERROR macros
- Implement proper Try/Catch blocks
- Always TROLLBACK on errors when $TLEVEL > 0
- Provide meaningful error messages with context
- Create service-specific exception classes
- Log errors with full stack trace
- Don't expose internal implementation details in errors
- **CRITICAL**: Cannot use argumented QUIT within Try/Catch blocks
  - Initialize return variable before Try
  - Set return value within Try
  - Use argumentless QUIT in Try/Catch
  - Return variable after Try/Catch block

### Performance Considerations

[Source: architecture/coding-standards.md]
- Minimize transaction duration to reduce lock contention
- Batch operations where appropriate
- Use efficient SQL queries via Table Module
- Cache frequently accessed lookup data
- Profile transaction execution times
- Monitor lock wait times and deadlocks
- Consider async operations for non-critical workflows
- Use connection pooling for high-volume services

### Security Considerations

- Implement service-level authorization checks
- Validate all input data before processing
- Sanitize error messages to prevent information leakage
- Audit all service operations for compliance
- Encrypt sensitive healthcare data (HIPAA compliance)
- Use secure session management
- Implement rate limiting for service operations
- Log security events and access patterns

### API Design Principles for Service Layer

- **Coarse-Grained Operations**: Service methods represent complete use cases, not individual data operations
- **Use Case Oriented**: Name methods after business operations (AdmitPatient, not CreatePatientRecord)
- **Consistent Return Types**: Use %Status or service result objects consistently
- **Versioning**: Plan for API versioning from the start
- **Documentation**: Document all service operations with parameters, return values, and side effects
- **Idempotency**: Design operations to be safely retryable where possible
- **Error Semantics**: Clear error codes and messages for each failure scenario
- **Context Objects**: Use service context for request metadata (user, timestamp, trace ID)

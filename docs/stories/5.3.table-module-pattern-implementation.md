### Class Structure Template for Table Module Pattern

[Source: architecture/coding-standards.md]
```objectscript
/// PoEAA Table Module Pattern - One Class Per Database Table
Class Patterns.PoEAA.DomainLogic.TableModule Extends %RegisteredObject
{
    /// Table name this module operates on
    Parameter TABLENAME;
    
    /// Find record by ID (class method - no instance needed)
    ClassMethod FindById(pId As %Integer) As %DynamicObject
    {
        Set tResult = ""
        Try {
            &sql(SELECT * INTO :tData FROM TableName WHERE ID = :pId)
            If SQLCODE = 0 {
                Set tResult = ..ResultToObject(tData)
            }
        } Catch ex {
            // Error handling
        }
        Quit tResult
    }
    
    /// Insert new record
    ClassMethod Insert(pData As %DynamicObject) As %Status
    {
        Set tSC = $$$OK
        Try {
            // Validate data
            Set tSC = ..ValidateData(pData)
            If $$$ISERR(tSC) Quit
            
            // Execute INSERT
            &sql(INSERT INTO TableName VALUES (:pData))
            If SQLCODE '= 0 {
                Set tSC = $$$ERROR($$$GeneralError, "Insert failed: " _ SQLCODE)
            }
        } Catch ex {
            Set tSC = ex.AsStatus()
        }
        Quit tSC
    }
    
    /// Update existing record
    ClassMethod Update(pId As %Integer, pData As %DynamicObject) As %Status
    {
        Set tSC = $$$OK
        Try {
            &sql(UPDATE TableName SET Fields = :pData WHERE ID = :pId)
            If SQLCODE '= 0 {
                Set tSC = $$$ERROR($$$GeneralError, "Update failed: " _ SQLCODE)
            }
        } Catch ex {
            Set tSC = ex.AsStatus()
        }
        Quit tSC
    }
    
    /// Delete record
    ClassMethod Delete(pId As %Integer) As %Status
    {
        Set tSC = $$$OK
        Try {
            &sql(DELETE FROM TableName WHERE ID = :pId)
            If SQLCODE '= 0 {
                Set tSC = $$$ERROR($$$GeneralError, "Delete failed: " _ SQLCODE)
            }
        } Catch ex {
            Set tSC = ex.AsStatus()
        }
        Quit tSC
    }
}
```

### Table Module Pattern Specific Considerations

- **One Class Per Table**: Each table module corresponds to a single database table
- **Static Methods**: All operations are class methods (no instance required)
- **SQL-Centric**: Pattern leverages SQL for data access and manipulation
- **Result Set Handling**: Convert SQL result sets to objects/collections
- **Table-Wide Operations**: Methods operate on the entire table or filtered subsets
- **No Business Logic in Objects**: Logic stays in table module class, not domain objects
- **Simple Data Structures**: Use %DynamicObject or simple data holders for results
- **Performance**: Efficient for set-based operations and reporting queries

### IRIS SQL Integration Features

[Source: architecture/tech-stack.md]
- **Embedded SQL**: &sql() syntax for inline SQL in ObjectScript methods
- **Dynamic SQL**: %SQL.Statement for runtime-constructed queries
- **Parameter Binding**: Automatic type conversion and SQL injection prevention
- **Result Sets**: %SQL.StatementResult for cursor-based iteration
- **SQLCODE**: Return code indicating success (0) or error conditions
- **%ROWCOUNT**: Number of rows affected by last SQL operation
- **Cursors**: Declare and manage database cursors for large result sets
- **Transactions**: SQL operations participate in TSTART/TCOMMIT transactions
- **Indices**: Leverage IRIS indices for query optimization
- **SQL Projections**: Persistent classes automatically project to SQL tables

### Table Module vs Other Domain Logic Patterns

- **Table Module vs Transaction Script**: Table Module organizes by table, Script by use case
- **Table Module vs Domain Model**: Table Module uses static methods and simple data, Domain Model uses rich objects with behavior
- **Table Module vs Service Layer**: Table Module IS data access layer, Service Layer coordinates business operations
- **When to use Table Module**: Record-set processing, reporting, table-oriented operations, minimal business logic
- **When NOT to use**: Complex business rules, rich domain behavior, object relationships

### Key Implementation Notes for Table Module Pattern

- Focus: One class per database table with static methods for table operations
- SQL-centric approach with embedded SQL and dynamic queries
- Healthcare context: Patient table CRUD operations with medical data validation
- All operations via class methods (no instance creation needed)
- Simpler than Domain Model but more organized than Transaction Script
- This is the third pattern in Epic 5 (PoEAA Domain Logic patterns)
- Contrast with Transaction Script's use-case organization and Domain Model's rich objects
- Document clear guidance on when to use Table Module vs other patterns
- Emphasize SQL integration and set-based operations

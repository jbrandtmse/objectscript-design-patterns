### Class Structure Template for Domain Model Pattern

[Source: architecture/coding-standards.md]
```objectscript
/// PoEAA Domain Model Pattern - Rich Business Objects with Encapsulated Behavior
Class Patterns.PoEAA.DomainLogic.DomainModel Extends %RegisteredObject
{
    /// Business data properties
    Property DomainData As %String;
    
    /// Validation rules collection
    Property ValidationRules [ MultiDimensional ];
    
    /// Validate business rules
    Method ValidateRules() As %Status
    {
        Set tSC = $$$OK
        Try {
            // Check all business rules
            If '..CheckInvariants() {
                Set tSC = $$$ERROR($$$GeneralError, "Business rules violated")
            }
        } Catch ex {
            Set tSC = ex.AsStatus()
        }
        Quit tSC
    }
    
    /// Check domain invariants
    Method CheckInvariants() As %Boolean
    {
        // Implement invariant checking logic
        Quit 1
    }
    
    /// Execute business logic
    Method ExecuteBusinessLogic() As %Status
    {
        Set tSC = $$$OK
        Try {
            // Validate first
            Set tSC = ..ValidateRules()
            If $$$ISERR(tSC) Quit
            
            // Execute domain logic
            // Business behavior here
            
        } Catch ex {
            Set tSC = ex.AsStatus()
        }
        Quit tSC
    }
}
```

### Domain Model Pattern Specific Considerations

- **Rich Objects**: Domain objects contain both data AND behavior (not anemic)
- **Business Logic Encapsulation**: Business rules live within domain objects
- **Object Relationships**: Models complex relationships between domain entities
- **Invariant Checking**: Domain objects maintain their own consistency
- **Domain Events**: Objects can raise events for significant state changes
- **Aggregate Roots**: Define consistency boundaries for related objects
- **Identity**: Each domain object has unique identity separate from database ID
- **Testability**: Business logic is easily testable without database

### Healthcare Clinical Domain Model Requirements

- **Patient Domain Object**: Demographics, medical history, allergies, active medications
- **Diagnosis Domain Object**: ICD-10 codes, diagnosis date, severity, clinical notes
- **Treatment Domain Object**: Treatment protocols, medication orders, dosage calculations
- **MedicalRecord Aggregate Root**: Coordinates Patient-Diagnosis-Treatment relationships
- **Business Rules**: Drug interaction checking, contraindication validation, dosage limits
- **Clinical Workflows**: Admission, diagnosis, treatment planning, discharge
- **Compliance**: HIPAA audit trails, consent management, data validation
- **Safety**: Medication safety checks, allergy checking, critical value alerts

### Domain Model vs Transaction Script Comparison

[Source: docs/patterns/poeaa/transaction-script.md]
- **Domain Model**: Rich objects with behavior, suitable for complex business logic
- **Transaction Script**: Procedural approach, suitable for simple CRUD operations
- **When to use Domain Model**: Complex business rules, frequent rule changes, rich behavior
- **When to use Transaction Script**: Simple operations, table-oriented processing
- **Complexity**: Domain Model has higher initial complexity but scales better
- **Maintainability**: Domain Model better for evolving requirements
- **Performance**: Transaction Script may be faster for simple operations
- **Testing**: Domain Model easier to unit test business logic in isolation

### ObjectScript Object Modeling Techniques

[Source: architecture/data-models.md]
- **Persistent Classes**: Use %Persistent for objects that need database storage
- **Serial Classes**: Use %SerialObject for embedded value objects
- **Registered Classes**: Use %RegisteredObject for transient domain objects
- **Relationships**: Use IRIS relationship properties (parent-children, one-to-many)
- **Validation**: Implement property validation with IsValid() methods
- **Calculated Properties**: Use calculated properties for derived values
- **Methods**: Encapsulate business logic in domain object methods
- **Properties**: Model domain concepts with appropriate datatypes

### IRIS Persistence Features for Domain Models

[Source: architecture/tech-stack.md]
- **Lazy Loading**: Use relationships with lazy loading for performance
- **Cascading Deletes**: Configure cascade behavior for related objects
- **Indices**: Create indices for frequently queried properties
- **SQL Projections**: Domain objects automatically project to SQL tables
- **Transactions**: Use TSTART/TCOMMIT for multi-object consistency
- **Locking**: Automatic concurrency control with object locking
- **Identity Maps**: IRIS maintains identity map within transaction
- **Queries**: Use object queries and SQL queries for data retrieval
